# Innernote — сайт для GitHub Pages

Четыре публичные страницы: главная, политика конфиденциальности, удаление аккаунта и поддержка. Использованы логотип, иллюстрации и демонстрационные экраны Innernote 3.0.6. Шрифт Lora поставляется локально вместе с OFL-лицензией.

## Публикация

1. Создайте **отдельный публичный** репозиторий `MarkoDurangDurango/innernote-site` и добавьте README при создании. Репозиторий Android-приложения `smer` остаётся закрытым.
2. Загрузите папку **`docs`** целиком, `build_site.py` и этот README в корень ветки `main`. Файл главной страницы должен лежать по пути `docs/index.html`. Не загружайте ZIP как единственный файл.
3. В репозитории откройте **Settings → Pages → Build and deployment**. Выберите **Deploy from a branch**, ветку **main**, папку **/docs** и нажмите **Save**.
4. В **Custom domain** укажите `innernote.ru` и сохраните. Файл `CNAME` уже содержит это имя. Настройте домен в Pages **до** изменения DNS.
5. В DNS Beget измените только записи сайта, как указано ниже. NS-серверы Beget и все записи Resend для `mail.innernote.ru` сохраняются.
6. Дождитесь проверки DNS и выпуска сертификата в GitHub Pages, затем включите **Enforce HTTPS**. Проверка и выпуск сертификата могут занять время; если переключатель пока недоступен, сначала дождитесь успешного DNS check.

Бесплатное размещение GitHub Pages требует публичного репозитория. Сайт не содержит ключей API, JSON сервисного аккаунта или кода Android-приложения.

## DNS в Beget

Для основного домена `innernote.ru` замените прежнюю A-запись хостинга на четыре A-записи:

| Имя | Тип | Значение |
|---|---|---|
| `@` / основной домен | A | `185.199.108.153` |
| `@` / основной домен | A | `185.199.109.153` |
| `@` / основной домен | A | `185.199.110.153` |
| `@` / основной домен | A | `185.199.111.153` |
| `www` | CNAME | `markodurangdurango.github.io.` |

У `www` не должно одновременно быть CNAME и A/AAAA. Если для основного домена осталась AAAA старого хостинга, уберите именно её либо настройте адреса IPv6 GitHub Pages по официальной инструкции. Служебные записи почты в других подзонах не меняются.

**Сохраняются:** NS Beget; DKIM `resend._domainkey.mail`; CNAME `send.mail` и `rsend.mail`; TXT `_dmarc`; другие записи, не относящиеся к маршрутизации сайта.

Справка GitHub: https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site

Дополнительная защита владения доменом: в настройках **аккаунта GitHub → Pages** можно добавить `innernote.ru` как verified domain, затем внести предложенную GitHub TXT-запись в Beget. Конкретный код берётся из интерфейса аккаунта, а не из этого архива.

## Обработка запросов удаления

Запрос по email обрабатывает разработчик. Страница сайта не подключает Firebase Admin и сама ничего не удаляет.

1. Проверьте принадлежность адреса аккаунта заявителю. При отсутствии доступа к адресу нужна отдельная проверка; не запрашивайте пароль или тексты дневника.
2. В Firebase Authentication найдите аккаунт по email и зафиксируйте UID для работы с Firestore.
3. Удалите **все документы во всех подколлекциях** `users/{uid}` и сам документ профиля. Состав коллекций нужно сверять с `syncedKinds` в актуальном `CloudRepository.kt`; в нативной версии это записи, экспозиции, карточки, подготовка к встрече и `aiReports`.
4. После удаления облачных документов удалите учётную запись в Firebase Authentication. Само по себе удаление пользователя Authentication не удаляет документы Firestore.
5. Сообщите пользователю о завершении. Локальные записи и сохранённые им экспорты остаются на его устройствах; сайт объясняет отдельное удаление этих данных.

Не используйте сервисный JSON `innernote-mail` для администрирования: у него намеренно ограниченные права на отправку писем. Не добавляйте административные ключи в этот сайт или публичный репозиторий.

Политика содержит только известные функции и сроки: локальное хранение до удаления, облачные данные до удаления аккаунта, очередь писем 30 минут, серверные ключи ограничений до 48 часов, стандартное хранение данных писем Resend 30 дней; для очистки данных Authentication в системах Google указан срок до 180 дней после удаления пользователя. Фиксированный срок ручной обработки запросов или хранения переписки поддержки не выдуман; при изменении фактических правил обновите публичный текст.

Разработчик обозначен как `Innernote / MarkoDurangDurango`, контакт взят из опубликованной конфигурации сервиса писем: `ar.ar.matevosian@gmail.com`. Если в Google Play используется другое имя разработчика или другой контакт, согласуйте информацию на сайте до отправки на модерацию.

## Обновление сайта

`build_site.py` собирает HTML в `docs` без зависимостей. CSS и исходные изображения находятся в `docs/assets`. После изменения текстов запустите:

```text
python build_site.py
```

Для публикации обновите папку `docs` в репозитории. Когда приложение появится в Google Play, замените сообщение о подготовке к публикации на настоящую ссылку магазина; фиктивной кнопки магазина сейчас нет.

Источники содержимого: `PRIVACY.md`, `CloudRepository.kt`, `AccountScreens.kt`, `ProfileScreen.kt`, `InnernoteStyle.kt` из версии Android 3.0.6/3.0.7; собственный почтовый Worker и его дополнение к политике. Изображения взяты из коммита `1d45848d051404d624ab8da2731f85c1f2568e2a` закрытого репозитория приложения.

## Проверка

При подготовке проверяются локальные ссылки, якоря, наличие изображений и шрифта, HTML-структура, ссылка запроса удаления и отсутствие секретов. Проверка в браузере и доступность на реальном домене подтверждаются отдельно после включения Pages и настройки DNS.
